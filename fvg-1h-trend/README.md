# fvg-1h-trend — стенд для бэктеста «FVG 1h по тренду»

Одна параметризованная стратегия `fvg_1h_trend_v1.pine`, через инпуты реализующая матрицу
**3 входа × 3 стопа × 3 тейка × 3 фильтра направления** плюс сессионный фильтр, режим
митигации wick/close и ветку IFVG. Прогоны — вручную, по одному изменению за раз.

ТЗ: `TZ_fvg-1h-trend_v1.md`. Контекст: «голый» FVG даёт PF≈1.0, эдж (если он есть) появляется
только от фильтров и риск-менеджмента — стенд должен это либо показать, либо отбраковать.

**Рабочий файл — `fvg_1h_trend_v1_1.pine`.** `fvg_1h_trend_v1.pine` оставлен рядом: он нужен
для регрессионной сверки патча тайм-стопа (этап 0, пункт 1) и после неё становится архивом.

**Статус: обе версии скомпилированы (0 ошибок, 0 предупреждений), на графике не прогонялись.
Этап 0 не выполнен.**

---

## 1. Установка и общие настройки

Инструменты: **EURUSD, GBPJPY, GER40, NAS100**, таймфрейм графика **1h**, окно — максимально
доступное (Deep Backtesting, если открыт).

Свойства стратегии (вкладка «Свойства», не инпуты):

| Параметр | Значение |
|---|---|
| Initial capital | 10 000 |
| Commission | **0.055 %** (percent) |
| Slippage | **3 тика**, для GBPJPY — **5** |
| Pyramiding | 0 |
| Recalculate on every tick | выкл |

Инпуты, которые меняются по инструменту:

| Инструмент | `stopBufferATR` | Сессии |
|---|---|---|
| EURUSD, NAS100 | 0.1 | окна 1–2 |
| GBPJPY, GER40 | **0.3** (волатильность, выбивание тенями) | GER40 — включить окно 3 `0300-0500:1234567` |

⚠️ Прогон без издержек не принимается. Проверка, что издержки реально применились, —
поле **«комиссии $…»** в первой строке таблицы: если там 0, комиссия не включена.
Проскальзывание из Pine не читается, его придётся сверять глазами во вкладке «Свойства».

## 2. Оси матрицы → инпуты

| Ось | Инпут | Варианты | База |
|---|---|---|---|
| A · вход | `entryMode` | `proximal` / `ce` / `distal` | **ce** |
| B · стоп | `stopMode` | `distalBuf` / `originCandle` / `swing` | **distalBuf** |
| C · тейк | `tpMode` | `rr2` / `rr3` / `liquidity` | **rr2** |
| D · тренд | `trendMode` | `none` / `ema200` / `htfBos` | **ema200** |
| M · митигация | `mitigationMode` | `close` / `wick` | **close** |
| S · сессии | `sessionFilter` | вкл / выкл | **выкл** |
| IFVG | `ifvgMode` | `remove` / `flip` | **remove** |
| — | `maxBarsInTrade` | 0–500 | **0 (выкл)** |

**Базовая конфигурация:** `ce / distalBuf / rr2 / ema200 / close / session off`.

`maxBarsInTrade` — **диагностический тайм-стоп, в матрицу этапов 1–6 не входит.** В формат имени
прогона он не добавлен, но его состояние печатается в той же строке таблицы рядом с именем
(`v1.1 TS=off` или `v1.1 TS=42`) — чтобы по скриншоту всегда было видно, с чем считался прогон.
Default 0 = выключен, поток ордеров при этом совпадает с v1. Позиция закрывается
по рынку, прожив указанное число баров; отсчёт идёт от бара входа и частичной фиксацией
не сбрасывается. Инструмент заведён заранее — чтобы, когда этап 1 покажет многодневные висяки
(на 1h с тейком до ликвидности они почти гарантированы), не перепрогонять базу на новой версии.

Имя прогона строится стратегией само и печатается первой строкой таблицы:

```
INSTRUMENT_A-{entry}_B-{stop}_C-{tp}_D-{trend}_M-{wick|close}_S-{on|off}[_P][_IFVGflip]
```

`_P` появляется при включённой частичной фиксации, `_IFVGflip` — в ветке flip. Этим же именем
подписывается строка в таблице результатов ниже — таблица попадает в скриншот целиком.

### Порядок инпутов и внешние прогонщики

`in_N` присваиваются по порядку объявления: `in_0` = `atrLen` … `in_34` = `splitTime`,
`in_35` = `maxBarsInTrade`. Полный порядок — в файле стратегии сверху вниз.
**Новые инпуты добавлять только в конец**, иначе поедут все сохранённые оверрайды.

`maxBarsInTrade` объявлен последним намеренно: он получает свободный `in_35` и не сдвигает
ни один инпут v1. В окне настроек он всё равно показывается в группе «Риск» — группа задаётся
параметром `group`, а не местом объявления.

По аналогии с MSNR (32 инпута → `commission_value` = `in_37`) здесь при 36 инпутах ожидается
`commission_value` = `in_41`, `slippage` = `in_42`. Это экстраполяция по одной точке —
перед первым автоматическим прогоном проверить фактическую нумерацию, а не верить на слово.

## 3. Что читать в таблице метрик

Таблица в правом верхнем углу, семь строк.

1. **имя прогона** + ТФ + риск на сделку.
2. **тестер** — сделок / WR / PF / Net % / maxDD по закрытиям баров / уплачено комиссий.
3. **по входам** — главная строка. Один вход = одна запись, даже если TradingView разбил его
   на две сделки частичной фиксацией. `expR` считается как среднее `pnl / risk$` по фактическим
   деньгам, **не** формулой «winrate × RR» (та завышает результат, как только появляется
   выход не по стопу и не по тейку). Здесь же — доля времени в позиции.
4. **зоны** — найдено сырых FVG → отсеяно размером → отсеяно displacement → в пул; сколько зон
   получили касание и сколько дошли до CE.
5. **уход зон** — отработано / инверсий / флипов / истекло / снято прунингом / живых, и в конце
   **«баланс»**: `в пул − отработано − инверсии − истекло − прунинг − живых`. Обязан быть **0**;
   любое другое число означает, что зона исчезла из пула мимо учёта. Флипы в балансе
   не участвуют — перевёрнутая зона остаётся в пуле, а не покидает его.
6. **входы** — зон без валидного стопа, сколько баров вход блокировала сессия, сколько баров
   блокировала открытая позиция, входов, частичных фиксаций, закрытых тайм-стопом (N и % сделок),
   **«лимиток снято по смерти зоны»** и **«входов от снятой зоны»**. Последнее — ассерт,
   он обязан быть 0 в любом прогоне; см. пункт 5a чек-листа этапа 0.
7. **IS / OOS** — при включённом `useSplit`: N, WR, PF и expR до и после `splitTime`
   плюс расхождение PF в процентах (порог отбраковки — 30 %).

PF в строках 3 и 7 считается в R-единицах (сумма плюсовых R / сумма минусовых R), в строке 2 —
в деньгах из отчёта тестера. При постоянном риске в % от эквити они близки, но не тождественны.

## 4. План прогонов (one change rule)

Каждый этап — **одно** изменение от текущей лучшей конфигурации. Результат каждой ячейки
записывать в таблицу §5 сразу, до запуска следующей.

**Этап 0 — smoke-test.** База, EURUSD 1h, короткое окно (~3–6 месяцев), `maxBarsInTrade = 0`.
Семь пунктов ниже — приёмка патча и логики. **Fail любого пункта = фикс до этапа 1.**

| # | Проверка | Как смотреть | Итог | Комментарий |
|---|---|---|---|---|
| 1 | v1.1 при `maxBarsInTrade=0` даёт метрики, идентичные v1 | оба скрипта на одном окне, сверить строки «тестер» и «по входам» | — | не прогонялось |
| 2 | Лимитки ставятся и снимаются по жизненному циклу зоны | точки лимиток исчезают при Expired/Inverted/Filled | — | не прогонялось |
| 3 | Нет входов против тренда при `trendMode=ema200` | ни одного лонга на красном фоне и наоборот | — | не прогонялось |
| 4 | `strategy.exit` активен с бара входа | в списке трейдов нет сделок без стопа; выходы подписаны TP/SL | — | не прогонялось |
| 5 | Счётчики зон согласованы | поле **«баланс»** в строке «уход зон» = 0; плюс `найдено = размер + displ + в пул` | — | не прогонялось |
| 5a | Снятая зона снимает свою лимитку | «входов от снятой зоны» = **0** при «лимиток снято по смерти зоны» > 0; в списке трейдов нет входов от зон, снятых прунингом или по Expired | — | не прогонялось |
| 6 | Прунинг работает | на длинном окне нет ошибок переполнения массивов/боксов | — | не прогонялось |
| 7 | `mitigationMode` wick↔close меняет статистику | переключить и сверить метрики — они обязаны разойтись | — | не прогонялось |

Пункт 1 — регрессионный тест патча тайм-стопа. Диффа торговой логики между версиями нет:
единственная новая ветка исполняется только при `maxBarsInTrade > 0`, поэтому расхождение
метрик при нуле означает не «тайм-стоп работает не так», а ошибку в чём-то другом —
разное окно, разная докачка истории или разные «Свойства».

Пункт 5 в формулировке ТЗ не сходился бы: зоны, снятые **прунингом** при переполнении
`maxZonesSide`, не попадали ни в один счётчик ухода. В v1.1 добавлен счётчик прунинга и готовое
поле «баланс», чтобы проверка была настоящей, а не тавтологией. Ненулевой баланс = баг учёта.

**Пункт 5a — про снятие лимитки.** Лимитка не привязана к зоне навсегда: каждый бар кандидат
ищется заново по живому пулу, и если валидного кандидата нет, ветка `else` делает
`strategy.cancel`. Смерть зоны (секция 2) и прунинг (секция 3) отрабатывают **до** армирования
(секция 5), поэтому снятая зона перестаёт быть кандидатом уже на баре своей смерти, а её ордер
либо заменяется ценой другой зоны, либо снимается. Пережить бар своей смерти он не может.

Это утверждение об архитектуре, и чтобы оно проверялось, а не принималось на веру, в таблицу
выведены два поля:

- **«лимиток снято по смерти зоны»** — сколько раз механизм реально сработал. Если на окне
  это 0, пункт 5a не проверен: нужно окно, где прунинг и Expired гарантированно случались
  (уменьшить `maxZonesSide` до 3–5 и/или `expiryBars` до 10–15, чтобы спровоцировать оба).
- **«входов от снятой зоны»** — ассерт: при исполнении проверяется, что зона ордера жива
  на начало бара (секции смерти и прунинга к этому моменту ещё не отработали). **Обязан быть 0.**
  Любое другое число = ордер пережил снятие своей зоны, это баг и стоп до этапа 1.

Дополнительная сверка по списку трейдов: комментарий входа содержит id зоны (`L z123`) —
по нему видно, из какой именно зоны пришло исполнение.

Заодно глазами: «комиссии $» > 0, «живых» зон не упирается в `maxZonesSide`, число сделок
в отчёте совпадает с «входов» из строки 3 (расхождение на 1 нормально — последняя позиция
ещё открыта).

**Этап 1 — baseline.** База на всех четырёх инструментах, полное окно. Порог значимости —
≥100 сделок на инструмент. Если на EURUSD 1h сделок мало (исследование это предсказывает),
факт фиксируется, значимость набирается суммой инструментов.

**Этап 2 — ось D.** `none` → `ema200` → `htfBos`. Фильтр остаётся, только если PF растёт
при N≥100. Обязательно смотреть вариант `none`: если без фильтров система теряет деньги на
большой выборке, фильтр не создаёт эдж, а лишь режет число проигрышей.

**Этап 3 — ось A.** `proximal` / `ce` / `distal`. Критерий — **expR, не winrate**: `proximal`
завысит winrate при худшем RR.

**Этап 4 — оси B и C.** Сначала стопы от победителя этапов 2–3, потом тейки от победителя
по стопам. Для `swing` следить за счётчиком «зон без валидного стопа» — если он большой,
ветка отбраковывается не по эджу, а по нехватке сетапов, это разные выводы.

**Этап 5 — митигация и IFVG.** `close` vs `wick`; затем `remove` vs `flip`. Ветка `flip`
принимается только при положительной добавке к матожиданию.

**Этап 6 — сессии и робастность.** `sessionFilter` on/off; затем `useSplit` = вкл и сверка
IS/OOS на лучшей конфигурации, плюс сверка между инструментами.

**Критерии отбраковки (жёсткие, зафиксированы до прогонов):**

- PF < 1.3 при ≥100 сделок с издержками → ветка отбракована;
- Exp R ≤ 0 → отбракована независимо от winrate;
- расхождение PF между IS и OOS > 30 % → переоптимизация, не принимается;
- работает только на одном инструменте → в отбракованные с пометкой;
- фильтр, не поднимающий PF, снимается (не тащить сложность).

Отчёты по этапам складывать в `docs/` рядом с этим файлом.

## 6. Устройство скрипта (что важно знать при чтении цифр)

**Зоны пересканируются на каждом баре целиком.** Снапшота пула на баре сигнала нет — это
прямой урок из smc-2koleno-v24, где разовое снятие POI выбрасывало из пула FVG, образованный
импульсом самого входа. Здесь такой FVG попадает в пул сразу.

**Одна лимитка на сторону, а не по одной на каждую зону.** Берётся ближайшая к цене валидная
зона нужного направления — именно её уровень цена достигнет первой, поэтому при `pyramiding=0`
это поведенчески эквивалентно лимиткам во всех зонах, но не создаёт риска переворота позиции
встречным ордером. Лонговая и шортовая лимитки связаны OCA и снимают друг друга при исполнении.

**Стоп жив с бара исполнения.** `strategy.exit` выставляется вместе с лимиткой, ещё до её
исполнения, поэтому на баре входа стоп уже активен. Без этого приёма первый бар сделки остаётся
без защиты, и результат систематически завышается.

**Лимитка ставится только по ту сторону рынка.** Если расчётный уровень входа оказался с
неправильной стороны от текущей цены (цена уже прошла зону), зона в этом баре не арминится —
иначе движок исполнил бы «лимитку» мгновенно по лучшей цене, чего в реальности не бывает.

**Стоп никогда не внутри зоны.** Если расчётный стоп попадает внутрь зоны (актуально для
`originCandle` и `swing`), зона не торгуется вообще и один раз попадает в счётчик «зон без
валидного стопа».

**Сессионный фильтр снимает лимитки вне окна.** ТЗ говорит «новые лимитки не ставятся»;
здесь висящие ордера вне окна ещё и снимаются. Причина: при `process_orders_on_close=false`
ордер, выставленный на закрытии последнего бара сессии, исполнялся бы уже следующим баром —
за окном. Открытая позиция ведётся до стопа/тейка независимо от сессии, как и требует ТЗ.

**`htfBos` отстаёт на один закрытый бар 4h.** `request.security` с `lookahead_off` плюс `[1]`
на серии: bias не переобувается внутри формирующейся 4h-свечи. Это правило репозитория,
цена — один бар задержки на смене структуры.

## 7. Известные ограничения

**Отклонения от ТЗ (утверждены в ТЗ v1.1, не пересматриваются):**

1. **Хранение зон — массив объектов, а не параллельные массивы.** Набор полей тот же
   (уровни, состояние, время создания, ссылка на box), но индексы не могут разъехаться при
   удалении зоны из середины пула. Требование «пересканировать, а не снапшотить» выполнено.
2. **Комиссия 0.055 %, не 0.05 %.** Стандарт репозитория (`CLAUDE.md`) — ради сопоставимости
   с уже посчитанными SMC/MSNR/CRT. Меняется во вкладке «Свойства».
3. **`process_orders_on_close = false`.** Входы лимитные: с `true` ордер исполнялся бы по цене
   закрытия бара сигнала, то есть оптимистичнее реальности. В CLAUDE.md репозитория заведено
   явное исключение для стратегий с лимитными входами, так что правило больше не нарушается молча.
4. **Проскальзывание 3 тика по умолчанию** (ТЗ: 2–3). Взят верх диапазона.
5. **Диагностика приёмки сверх ТЗ v1.1:** счётчик прунинга и поле «баланс» (пункт 5),
   «лимиток снято по смерти зоны» и ассерт «входов от снятой зоны» (пункт 5a).
   Без них оба приёмочных пункта не проверяемы. Только учёт, на поток ордеров не влияет.

**Ограничения движка и методики:**

6. **Открытая позиция блокирует новые сетапы.** На SMC ровно это дало 45 % календарного
   времени в позиции и сломало сравнимость A/B: часть сетапов отбрасывается по причине,
   не связанной со сравниваемой осью. Поэтому в таблицу выведены **«в позиции X % времени»**
   и **«занято позицией N баров»** — если между ячейками матрицы эти числа сильно расходятся,
   сравнение уже нечестное, и до выводов нужно чинить не тейк, а блокировку.
   Лекарство (`maxBarsInTrade`) в v1.1 есть, но по умолчанию **выключено**: включать его
   в середине матрицы нельзя — сравнивать можно только ячейки с одинаковым тайм-стопом.
7. **Тайм-стоп исполняется на открытии следующего бара, а не на закрытии текущего.**
   ТЗ v1.1 говорит «закрытие по рынку на закрытии текущего бара», но при
   `process_orders_on_close = false` рыночный ордер, выданный на закрытии бара, физически
   исполняется открытием следующего. Это на один бар позже и консервативнее; менять
   `process_orders_on_close` ради тайм-стопа нельзя — сломается исполнение лимитных входов,
   ради которого он и выставлен в false.
8. **Частичная фиксация (`partialTP`) удваивает число сделок в отчёте тестера** — TradingView
   считает каждое частичное закрытие отдельной сделкой. Строка «тестер» в этом режиме
   недостоверна по N и WR; читать строку «по входам».
9. **Размер позиции считается от цены лимитки, а не от фактического исполнения.** На гэпе
   ордер исполнится лучше уровня, и реальный риск окажется чуть меньше 1 % — в консервативную
   сторону. R при этом считается от фактической цены входа, то есть корректно.
10. **`maxDD` в таблице — по закрытиям баров**, внутрибарные просадки не учитываются.
    Просадка из отчёта тестера будет чуть больше; для отбраковки использовать отчёт тестера.
11. **`liquidity` без подходящего свинга падает на фиксированный `liqFallbackRR`** (по умолчанию
    2R). Если таких сделок много, ветка `liquidity` фактически измеряет смесь двух режимов.
12. **Дробное количество контрактов** на GER40/NAS100 движок разрешает; в реальности лот
    округляется, и мелкие сделки исполнялись бы иначе.
13. **Глубина истории.** Свежий график TradingView отдаёт ~300 баров — без докачки истории
    бэктест считается по нескольким суткам и выглядит пустым. Перед прогоном прокрутить график
    в начало нужного окна и убедиться, что «сделок» в отчёте соответствует окну.
14. **Ветка `ifvgMode = flip` торгуется по тому же фильтру тренда**, что и обычные зоны.
    Перевёрнутая зона, направление которой против активного тренда, торговаться не будет —
    это делает ветку flip заведомо более редкой; читать её N отдельно.
